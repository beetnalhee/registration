# 배정 알고리즘

## 요약

```
1) 나이(만나이) 계산 → 기본 그룹 결정
2) 트랜잭션 시작 + advisory lock  ← 여기서부터 배정은 한 건씩만 진행
3) 참가자가 고른 회차의 (회차, 성별) 정원 확인
   마감이면 → 그 회차의 대기자 (다른 회차로 넘기지 않음, 선착순)
4) 자리가 있으면 그 회차 안에서 그룹 결정 (Bridge Zone 만 이동 가능)
5) 좌석 점유 + 참가번호 발급 + 참가자 저장
6) 커밋 → 이메일 발송
```

## 선착순인 이유

회차를 3순위까지 받아 자동으로 내려보내던 방식을 버렸다. 참가자가 스스로
취소할 수 있게 되면서, **열린 자리를 누가 기다리고 있는지가 명확해야**
승격 판단이 단순해졌기 때문이다.

3순위 방식에서는 "2회차 자리가 하나 열렸을 때 2회차를 2순위로 적은 사람과
3순위로 적은 사람 중 누구를 올릴지"가 애매했다. 지금은 그 회차를 고른
사람들의 신청 순서대로 올리면 된다.

## 구현 위치

핵심 코드는 `server/domain/assignment.ts` 의 `decideAssignment()` 이며,
DB·시간·난수를 모르는 순수 함수입니다. 상태 변경은 호출자가 트랜잭션 안에서 수행합니다.

## 1. 연령 → 그룹

만나이는 `(연, 월, 일)` 튜플 비교로 계산합니다. `Date` 산술을 쓰지 않아 서버 타임존과
일광절약시간에 영향을 받지 않습니다.

```
기준일 = event_settings.event_date (행사 당일)

만 18~25세 → SUMMER
만 26~35세 → NIGHT
그 밖       → 신청 거절 (참가 가능 연령 범위만 안내)
```

연령 구간은 `groups` 표의 데이터입니다. 코드를 고치지 않고 조정할 수 있습니다.

## 2. Bridge Zone (내부 운영 규칙 · 비노출)

> ⚠️ 이 절의 내용은 참가자에게 어떤 형태로도 노출되지 않습니다.
> API 응답, 화면 문구, 오류 메시지, 이메일에 등장하지 않습니다.

만 **24 · 25 · 26 · 27세**는 두 그룹 어디로든 배정될 수 있습니다.

### 왜 필요한가

3분 데이트는 같은 그룹끼리 짝을 짓습니다. 그런데 하드 정원은 `(회차, 성별)` 단위이므로
그룹별 인원은 신청 순서에 따라 얼마든지 기울 수 있습니다.

```
1회차 (남 20 / 여 20 — 정원은 맞지만)
  SUMMER  남 14  여  4     ← 남성 10명이 짝을 못 만난다
  NIGHT   남  6  여 16     ← 여성 10명이 짝을 못 만난다
```

경계 연령 참가자를 부족한 쪽으로 흘려보내 이 상황을 예방합니다.

### 그룹 선택 점수

```
성비 결손(deficit) = 그 그룹의 (반대 성별 수 − 내 성별 수)
                     양수 = 내 성별이 부족하다 = 내가 들어가면 짝이 맞아진다

점수(그룹) = deficit × balanceWeight + (기본 그룹이면 defaultGroupBonus)

기본값: balanceWeight = 1, defaultGroupBonus = 2
점수가 높은 그룹으로 배정. 동점이면 기본 그룹 유지.
```

`defaultGroupBonus = 2` 이므로 **반대 그룹의 결손이 기본 그룹보다 3명 이상 클 때만** 이동합니다.
즉 평소에는 나이에 맞는 그룹을 유지하고, 한쪽이 실제로 무너질 때만 개입합니다.

가중치는 `server/config/policy.ts` 의 `BALANCE_POLICY` 한 곳에서 조정합니다.

### 예시

| 상황 | 결과 |
|---|---|
| 24세 여성 / SUMMER 균형, NIGHT 남3 여0 (결손 3) | → **NIGHT** (3 > 0+2) |
| 24세 여성 / SUMMER 균형, NIGHT 남2 여0 (결손 2) | → SUMMER 유지 (2 = 0+2, 동점) |
| 30세 여성 / SUMMER 남10 여0 (결손 10) | → NIGHT 유지 (Bridge Zone 아님) |
| 26세 남성 / SUMMER 남0 여9, NIGHT 균형 | → **SUMMER** (9 > 0+2) |

## 3. 회차는 참가자가 정하고, 그룹만 시스템이 정한다

하드 정원이 `(회차, 성별)` 단위이므로 그룹은 회차의 가용성에 영향을 주지 않습니다.
따라서 절차가 단순합니다.

```
if round_capacity(고른 회차, 내 성별).filled < capacity:
    그룹 결정 → 배정
else:
    그 회차의 대기자
```

참가자는 회차만 고르고, 그룹은 시스템이 성비를 보며 정합니다.
그룹 성비는 **고른 회차**의 값만 봅니다.

## 4. 동시 신청 처리 (Race Condition)

두 겹으로 막습니다.

### 1겹 — advisory lock 으로 직렬화

```sql
BEGIN;
  SELECT pg_advisory_xact_lock(918273645);   -- 배정 임계 구역 진입
  -- 정원·성비 조회
  -- 배정 결정
  UPDATE round_capacity SET filled_count = filled_count + 1
   WHERE round_id = ? AND gender = ? AND filled_count < capacity;
  UPDATE group_tally  SET active_count = active_count + 1,
                          seq_counter  = seq_counter + 1 ...;
  INSERT INTO participants ...;
COMMIT;   -- 락 자동 해제
```

- 락을 잡은 트랜잭션이 끝날 때까지 다른 배정은 대기합니다.
  → "정원 확인 → 카운터 증가" 사이에 다른 신청이 끼어들 수 없습니다.
- `pg_advisory_xact_lock` 은 트랜잭션 범위이므로 **연결을 반납해도 락이 남지 않고**,
  Supabase transaction pooler(PgBouncer, port 6543) 에서도 안전합니다.
- 신청·대기자 승격·회차 변경·취소가 **모두 같은 키**를 잡습니다.

### 2겹 — DB 제약으로 커밋 거부

```sql
constraint round_capacity_not_exceeded check (filled_count <= capacity)
```

애플리케이션에 버그가 있어도 21번째 행은 커밋되지 않습니다.
추가로 `UPDATE ... WHERE filled_count < capacity` 조건이 있어, 락이 없더라도
정원을 넘겨 갱신되는 일은 없습니다(0행 반환 → 재시도 안내).

### 락 점유 시간 최소화

| 락 밖에서 | 락 안에서 |
|---|---|
| 입력 검증(zod), 설정 조회, 만나이 계산, 연령 자격 판정, 회차 존재 확인 | 정원·성비 조회, 배정 결정, 카운터 증가, INSERT |
| 이메일 발송 (커밋 후) | |

이메일 발송을 트랜잭션 안에 넣으면 SMTP 응답을 기다리는 동안 모든 신청이 멈춥니다.
그래서 커밋 후에 발송하고, 실패해도 신청은 성공으로 처리합니다.

### 실측 검증

`tests/integration/concurrency.test.ts` 가 실제 PostgreSQL 로 확인합니다.

| 시나리오 | 기대 | 결과 |
|---|---|---|
| 40명이 동시에 1회차 신청 | 배정 20 / 대기 20, 2·3회차는 0명 | ✅ |
| 배정된 참가번호 20개 | 중복 0 | ✅ |
| 회차를 나눠 동시 신청 (정원 3) | 회차별 3명씩 배정, 나머지 대기 | ✅ |
| 남 6 + 여 6 동시 (정원 3) | 성별별 3명씩, 서로 잠식 없음 | ✅ |
| 같은 이메일로 동시 2건 | 1건만 접수 | ✅ |

## 5. 참가번호

```
{그룹}-{회차}-{성별}-{순번}      예) SUMMER-2-F-013
```

- 순번은 `group_tally.seq_counter` 에서 발급합니다. 이 값은 **취소되어도 감소하지 않습니다.**
  → 취소된 번호가 다른 사람에게 재발급되지 않습니다.
- `participants.participant_code` 에 유니크 제약이 있습니다.
- 회차나 그룹을 변경하면 새 기준으로 **재발급**됩니다.
- 그룹 코드에 연령 정보가 없습니다. 명찰·좌석표에 노출되어도 연령대가 드러나지 않습니다.

## 6. 대기자

고른 회차가 마감이면 `status='waitlisted'`, `waitlisted_at=now()` 로 저장합니다.
대기 순번은 `waitlisted_at` 순서입니다.

### 승격

관리자가 `POST /api/admin/participants/:id/promote` 로 승격합니다.

```
회차 미지정 → 본인이 고른 회차를 먼저 보고, 없으면 나머지 회차에서 찾는다
그룹 미지정 → 신청 때와 같은 규칙(기본 그룹 우선 + 성비 보정)으로 정한다
빈자리가 없으면 → 거절 (관리자라도 정원 20명은 넘지 못한다)
```

승격도 같은 advisory lock 안에서 수행되므로 동시에 신청이 들어와도 정원을 넘지 않습니다.
승격 후 안내 메일이 자동 발송됩니다.

## 7. 취소와 좌석 반납

```
status = 'cancelled', cancelled_at = now()
round_capacity.filled_count −1     ← 좌석 반납
group_tally.active_count   −1      ← 성비 계산에서 제외
group_tally.seq_counter    유지     ← 번호 재사용 방지
```

취소된 참가자는 유니크 인덱스에서 제외되므로 **같은 이메일·연락처로 다시 신청할 수 있습니다.**

## 8. 회차 상태 계산

```
filled >= capacity                    → closed    ❌ 마감
filled / capacity >= threshold        → near_full 🔥 마감 임박
그 외                                  → open      ✅ 신청 가능

threshold = event_settings.near_full_threshold (기본 0.8, 관리자 변경 가능)
is_open = false 이면 모든 회차를 closed 로 표시
```

성별을 아는 경우(신청 2단계)는 해당 성별 정원만 봅니다.
성별을 모르는 경우(랜딩)는 남녀 상태를 합치되, **한쪽만 마감이면 `near_full`** 로 보여
어느 성별이 찼는지 드러내지 않습니다.

응답 필드는 `{ roundNo, availability }` 두 개뿐입니다.

## 9. 본인 취소

참가자는 `/lookup` 에서 **이메일 + 전화번호 뒤 4자리**로 본인 신청을 취소할 수 있습니다.

```
접수 중(is_open)일 때만 허용
  ↓
좌석 반납 + 출석 기록 정리 + 취소 메일   ← 관리자 취소와 완전히 같은 경로를 재사용
  ↓
audit_logs 에 admin_email='self-service(본인 취소)' 로 기록
```

- **되돌릴 수 없습니다.** 복구 기능을 두지 않았으므로 다시 참여하려면 새로 신청해야 하고,
  그때 자리가 없으면 대기자가 됩니다. 화면에서 2단계 확인으로 오조작을 막습니다.
- 취소 로직을 관리자 경로와 공유하는 이유: 좌석 반납·출석 정리·메일 발송이
  두 벌로 갈라지면 한쪽만 고쳐지는 사고가 납니다.
- 자격증명이 조회와 동일하므로 남의 이메일과 번호 뒤 4자리를 아는 사람은
  그 사람 신청을 취소할 수 있습니다. 분당 3회 요청 제한으로 완화합니다.
- 접수를 닫은 뒤에는 자리 재배치를 사람이 판단해야 하므로 운영진 문의로 유도합니다.
